# Анализ сложности и производительности

## 1. Используемые структуры данных

В проекте используются три структуры данных:

- **Динамический массив (Arr)** - основное хранилище задач.
- **Хеш-таблица (HashTable)** - быстрый поиск задачи по идентификатору.
- **Бинарная куча (Heap)** - выбор следующей задачи по приоритету. При равных приоритетах раньше выбирается задача, созданная раньше.

В таблицах ниже *n* - количество задач (или элементов рассматриваемой структуры). Указана асимптотическая сложность по времени.

## 2. Сложность операций структур данных

| Структура | Операция                     | Сложность            | Пояснение                                                                     |
| --------- | ---------------------------- | -------------------- | ----------------------------------------------------------------------------- |
| Arr       | Добавление в конец           | O(1) амортизированно | Обычно запись в свободную ячейку; при расширении копируются элементы за O(n). |
| Arr       | Доступ по индексу            | O(1)                 | Обращение к элементу массива по индексу.                                      |
| Arr       | Удаление по индексу          | O(n)                 | После удаления необходимо сдвинуть элементы.                                  |
| HashTable | Вставка                      | O(1) в среднем       | Вычисляется хеш и выбирается цепочка; расширение занимает O(n).               |
| HashTable | Поиск по ID                  | O(1) в среднем       | При большом числе коллизий возможна сложность O(n).                           |
| HashTable | Удаление                     | O(1) в среднем       | В худшем случае приходится просмотреть длинную цепочку за O(n).               |
| HashTable | Расширение                   | O(n)                 | Все записи распределяются по новой таблице.                                   |
| Heap      | Добавление                   | O(log n)             | Элемент поднимается по уровням кучи.                                          |
| Heap      | Просмотр верхнего элемента   | O(1)                 | Нужный элемент находится в корне кучи.                                        |
| Heap      | Извлечение верхнего элемента | O(log n)             | После удаления корня восстанавливается порядок кучи.                          |

## 3. Сложность операций TaskManager

| Метод             | Ожидаемая сложность                           | Пояснение                                                        |
| ----------------- | --------------------------------------------- | ---------------------------------------------------------------- |
| `createTask()`    | O(log n)                                      | Добавление в массив и хеш-таблицу, затем вставка в кучу.         |
| `getTask()`       | O(1) в среднем                                | Поиск индекса в хеш-таблице и обращение к массиву.               |
| `startNextTask()` | O(log n)                                      | Извлечение из кучи и изменение статуса.                          |
| `completeTask()`  | O(1) в среднем                                | Поиск задачи и смена статуса.                                    |
| `failTask()`      | O(1) в среднем, без учёта длины строки ошибки | Поиск задачи, запись ошибки и смена статуса.                     |
| `cancelTask()`    | O(1) в среднем                                | Поиск задачи и смена статуса.                                    |
| `listTasks()`     | O(n)                                          | Просмотр всех задач, при необходимости с фильтрацией по статусу. |
| `getStats()`      | O(n)                                          | Подсчёт задач по статусам при одном проходе.                     |
| `saveToFile()`    | O(n) без учёта объёма текстовых полей         | Последовательная запись всех задач в файл.                       |
| `loadFromFile()`  | O(n log n)                                    | Чтение задач и восстановление массива, хеш-индекса и очереди.    |

**Примечание:** отменённая задача может временно оставаться внутри кучи. При `startNextTask()` такие элементы пропускаются. Поэтому один вызов иногда извлекает несколько элементов и занимает больше времени, чем O(log n). При оценке файловых операций также необходимо учитывать суммарную длину строк задач и скорость диска.

## 4. Условия эксперимента

Эксперимент проводился со **100 000 задачами*. Проект собирается через CMake. Для измерения времени использовались chrono::steady_clock и миллисекунды.

Порядок проведения:

1. Создание 100 000 задач через `createTask()` с типом `test`, данными `payload` и приоритетами `i % 101` (от 0 до 100).
2. Поиск всех созданных задач по ID от 1 до 100 000 через `getTask()`.
3. Последовательное извлечение 100 000 задач через `startNextTask()`.
4. Получение числа расширений хеш-таблицы и максимального зарегистрированного коэффициента заполнения.

Измерения каждого этапа проводились отдельно. Запись состояния на диск в измеряемые циклы не входила. Эксперимент повторялся **три раза**.

### Сборка и запуск

Из корневой папки проекта:

```bash
cmake -S . -B build
cmake --build build
./build/benchmark
```

Для воспроизведения среднего времени команду запуска бенчмарка нужно выполнить три раза.

## 6. Контрольная сумма

В бенчмарке при поиске и извлечении суммируются ID найденных задач:

```cpp
uint64_t searchSum = 0;
for (int i = 1; i <= N; i++) {
    Task* task = manager.getTask(i);
    searchSum += task->id;
}
```

Аналогично при извлечении используется `extractSum += task->id`.

Поскольку ID идут от 1 до 100 000, ожидаемая сумма равна:

`1 + 2 + ... + 100000 = 100000 * 100001 / 2 = 5000050000`.

Одинаковые правильные суммы показывают, что результаты поиска и извлечения согласуются с ожидаемыми ID. Это **простая проверка результатов**, а не криптографическая контрольная сумма: разные наборы ID теоретически могут дать одинаковую сумму. Тип `uint64_t` нужен, потому что результат больше максимального значения 32-битного знакового `int`.

## 7. Анализ результатов

Наименьшее время показал поиск по ID — **3,770 мс** на 100 000 запросов. Это согласуется с ожидаемым средним временем O(1) для хеш-таблицы.

Добавление заняло в среднем **528,433 мс**. Во время создания задача записывается в массив, добавляется в хеш-таблицу и помещается в бинарную кучу. Вставка в кучу имеет сложность O(log n); также выполняется создание строк и отметок времени.

Последовательное извлечение заняло в среднем **464,698 мс**. При каждом запуске следующей задачи куча перестраивается, что соответствует ожидаемой сложности O(log n) на операцию в обычном случае.

Во время эксперимента хеш-таблица расширялась **17 раз**, что связано с увеличением объёма хранимых задач. Контрольные суммы поиска и извлечения совпали с ожидаемым результатом.

**Вывод:** измерения не противоречат теоретической сложности реализованных структур данных. Они показывают заметное преимущество поиска по хеш-таблице перед операциями, связанными с поддержанием приоритетной очереди. Однако один размер входных данных сам по себе не доказывает асимптотическую сложность; для этого потребовались бы дополнительные эксперименты при разных значениях `n`.
